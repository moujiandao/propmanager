# PropManager

## What This Is
A property management web application built with Next.js and Supabase. Provides landlords tools for managing rental properties, units, tenants, leases, payments, maintenance, and documents. Tenants get a separate portal for payments, maintenance requests, and profile management.

## Architecture
- **Framework**: Next.js 16 (App Router, Turbopack)
- **Database & Auth**: Supabase (PostgreSQL + Auth + Storage)
- **Payments**: Stripe (ACH)
- **Email**: Resend
- **Styling**: Inline styles, **Inter** font (the in-app monolith loads it via inline `@import`; the public marketing/auth surfaces use `next/font` Inter + `app/globals.css`). The in-app palette is the `theme` object at the top of `property-management-app.jsx`; the public surfaces mirror it via `lib/theme.js` (`palette`/`btnStyle`)
- **Routing & public surface**: App Router **route groups** organize three surfaces (groups don't appear in URLs). `(marketing)` = public site: `/` (home) and `/pricing` (Free/Pro/Business flat tiers), light-themed server components. `(auth)` = `/login` (landlord/tenant role tabs; resolves role before navigating) and `/signup` (registers a free-tier landlord, auto-signs-in, lands on `/dashboard`). `(app)` = the monolith mounted at `/dashboard`, gated by a server-side auth guard in `app/(app)/dashboard/layout.js` (redirects to `/login?next=/dashboard` if no session). Shared brand mark in `app/_brand.jsx`, auth form primitives in `app/(auth)/_form.jsx`. `middleware.js` only refreshes the session cookie — gating lives in the dashboard layout, not middleware.
- **UI monolith**: `property-management-app.jsx` contains all landlord and tenant UI components. Mounted only at `/dashboard` and assumes an authed user (the login/signup screens were removed when the public auth routes were added). Navigation inside the dashboard is state-driven (`page` state), not URL-driven
- **Phase 2 components**: `phase2-components.jsx` holds `PropertyDetailPage` (a property's units grid + unit add/edit/delete, reached by clicking a property card), `TenantContactPage`, `DocumentsPageV2`, and `DocViewer`. Same circular-import pattern as the other component files. Only the units section and `TenantContactPage`'s delete action are bilingual (both pages now take a `t` prop); the rest of the file is still hardcoded English (pre-existing — translate what you touch)
- **Email Automation components**: `email-automation-components.jsx` holds `EmailAutomationPage` (Templates / Automations / Inbox tabs) and `BatchSendModal` (the "Run now" human-review batch send: preview → per-recipient review/edit → mandatory confirm dialog → send, backed by the `/api/email/batches` routes). Imports shared UI from `property-management-app.jsx` (circular import, same pattern as phase2-components)
- **Maintenance module**: `lib/maintenance/` is an isomorphic ESM module (own `package.json`) that is the persistence seam for the maintenance aggregate: `core.js` (React-free write ops + soft/hard-delete rule, takes an injected adapter), `adapter.js` (real adapter over the anon Supabase client + maintenance routes; `fake.js` is the in-memory test double), `mappers.js` (the one home for the aggregate's snake→camel shape — `fetchAllData` imports these). The monolith calls it through a `useMaintenanceMutations(setData)` hook that owns optimistic update + rollback. `status.js` is the home for the Status vocabulary (`columnOf` board mapping, `isOpen` for "open requests" counts, `normalizeWriteStatus` server validation) — shared by the board, the dashboard counts, and the create route so they can't drift. Unit-tested via `npm test`. First slice of a per-entity data-access seam; other entities still write directly.
- **Property module**: `lib/property/` is an isomorphic ESM module (own `package.json`), the fourth per-entity seam slice: `core.js` (`createProperty`/`deleteProperty`/`setDriveLink`), `adapter.js`/`fake.js`, `mappers.js` (`mapProperty`). Monolith calls it via `usePropertyMutations()`; property edit + image-upload stay in `app/api/properties/*` routes. Unit-tested via `npm test`.
- **Payment-reminders module**: `lib/payment-reminders/` is an isomorphic ESM module (own `package.json`), the third per-entity seam slice — for the older `email_settings` "Payment Reminders" feature (distinct from `lib/email` automation; see the Database Tables note). `constants.js` (default settings + the field→column map, formerly the inline `KEY_MAP`), `mappers.js` (`mapEmailSettings`), `core.js` (`setReminderField`/`saveTemplates`), `adapter.js`/`fake.js`. `EmailPage` writes via a `useEmailSettingsMutations()` hook. Unit-tested via `npm test`.
- **Tenant module**: `lib/tenant/` is an isomorphic ESM module (own `package.json`), the second slice of the per-entity data-access seam: `core.js` (tenant self-service profile writes — recurring-payment, bank-connected, display-name — React-free, adapter-injected), `adapter.js`/`fake.js`, and `mappers.js` (`mapTenant`, the one home for the tenant read-shape — the app's highest-touchpoint mapper). The monolith calls it via a `useTenantMutations()` hook; no direct `tenant_profiles` writes remain in the monolith. Landlord create/update/delete-tenant stay in their server routes. `deletion.js` is the one home for what blocks a tenant delete (`TENANT_DELETE_BLOCKERS`) — shared by `app/api/auth/delete-tenant` (which runs the counts) and the monolith's confirm modal (which renders the labels and pre-counts the same relations from loaded `data` via `blockersFromData`, advisory only — the route stays the authority), so the three can't drift. The confirm modal itself is `TenantDeleteModal`, **exported** from `property-management-app.jsx` because the tenant detail page in `phase2-components.jsx` also deletes from it — same rationale as `useUnitMutations`. `status.js` is the home for the tenant Status vocabulary — see **Tenant status is derived** under Non-Obvious Decisions. Unit-tested via `npm test`.
- **Parking module**: `lib/parking/` is an isomorphic ESM module (own `package.json`), the fifth per-entity seam slice: `core.js` (spot CRUD + lease create/end), `adapter.js`/`fake.js`, `mappers.js`, and `status.js` (lease-active derivation + the `SPOT_TYPES` vocabulary). Monolith calls it via `useParkingMutations()` and renders `ParkingPage`. Spot writes go straight through the anon client; lease creation goes through `app/api/parking/leases/create` because a new market renter needs its `parking_renters` and `parking_leases` rows created together with rollback. Unit-tested via `npm test`.
  - `layout.js` extends that module with the lot **diagram** geometry: pure, React-free, and derived entirely from each spot's `type` (see the Non-Obvious Decisions note). It takes the spots and returns `{ width, height, outline, stalls, unplaced }` — positioned SVG polygons plus the spots it couldn't place. The `ParkingLotDiagram` component in `property-management-app.jsx` only draws what it returns and owns the click-through to the spot-detail modal; all layout math stays here and is unit-tested via `npm test`.
- **Units module**: `lib/units/` is an isomorphic ESM module (own `package.json`), the sixth per-entity seam slice: `core.js` (`createUnit`/`updateUnit`/`deleteUnit`), `adapter.js`/`fake.js`, `mappers.js` (`mapUnit`). Called from `PropertyDetailPage` (in `phase2-components.jsx`) via `useUnitMutations()`, which is **exported** from `property-management-app.jsx` — the only seam hook that is, because its sole caller lives in the other component file. `deleteUnit` is guarded: it re-reads the linked-tenant count through the adapter (never the caller's possibly-stale `data.tenants`) and refuses while any tenant references the unit. `updateUnit` cannot move a unit between properties, same rationale as `updateSpot`. Neither write touches `status` — see Non-Obvious Decisions. Unit-tested via `npm test`.
- **Format module**: `lib/format/` is the canonical isomorphic formatting module (`fmt`, `fmtDate`, `daysBetween`), shared by the monolith, renewals, and `lib/email` (whose `format.js` re-exports from it). One home for the currency/date formatters; `fmtDate` carries the YYYY-MM-DD→local-midnight rule that must not drift. Unit-tested via `npm test`.
- **Email module**: `lib/email/` is an isomorphic ESM module (own `package.json` with `"type":"module"`) shared by the UI and server: `format.js` (now re-exports `lib/format`), `merge.js` (merge-tag rendering), `events.js` (event-date resolution), `context.js` (server snake→camel loaders), `audience.js` (`candidates`/`matchesScope` recipient matching, shared by the cron and the batch route so they never drift), `send.js` (Resend wrapper). Unit-tested via `npm test`
- **Email batch send (human review)**: `app/api/email/batches/` routes stage and send a reviewed batch from an automation. `route.js` (POST run-now: stage everyone matching the automation's event + scope as draft `email_messages` under one `email_batches` row, idempotent/resumable), `[id]/route.js` (PATCH per-recipient edits/adds/removes), `[id]/send/route.js` (POST: atomic `draft→queued` claim before each Resend send to prevent duplicates, no env kill-switch — the confirm dialog is the gate). The daily cron (`app/api/cron/email-automations`) stays the automatic path; this is the manual, human-gated path.
- **Lease-renewal (DocuSeal) feature**: `renewal-components.jsx` holds `RenewalsPage` (due queue → prepare → review gate → confirm-to-send), same circular-import pattern as the other component files. `lib/docuseal/` is an isomorphic ESM module (own `package.json`): `client.js` (DocuSeal API: create suppressed submission, release submitter, fetch signed PDF, HMAC webhook verify) and `renewal.js` (shared UTC term-derivation + original-lease-date selection, used by both the create route and the UI so they never drift). Unit-tested via `npm test`. Routes: `app/api/renewals/create`, `app/api/renewals/send`, `app/api/webhooks/docuseal`. Spec: `docs/docuseal-tenant-renewal-spec.md`. v1 excludes Phase 4 (Drive filing + auto lease-advance).
- **API routes**: `app/api/` for auth, payments, webhooks, and document operations
- **Supabase clients**: `lib/supabase/server.js` (service role), `lib/supabase/client.js` (anon key)
- **Auth callback**: `app/auth/callback/route.js` handles Supabase recovery/magic link flows
- **Agent instructions**: `AGENTS.md` is a thin pointer to this file (so `AGENTS.md`-aware tools like Codex find the same guide). This `CLAUDE.md` is the single source of truth — do not duplicate content into `AGENTS.md`.

## Database Tables
- `landlord_profiles` - landlord accounts; one row per **team**, not per auth user. Carries commercialization plan state: `plan` (default `'free'`, CHECK free/pro/business) + nullable `subscription_status`/`stripe_customer_id`/`stripe_subscription_id` placeholders for Phase 2 Stripe subscription billing (`scripts/add-landlord-plan.sql`). Billing logic + plan gating are not built yet (Phase 2/3)
- `landlord_members` - maps `auth.users` to a `landlord_id` (a team). Multiple auth users can be members of the same team. Login resolves the active landlord_id via this table; **do not** assume `auth.uid() === landlord_id`. Use the SQL helper `is_team_member(landlord_id)` in RLS policies.
- `tenant_profiles` - tenant accounts linked to landlords, properties, and units. The `status` column is **write-only legacy** — status is derived from `move_in_date`/`move_out_date` (see Non-Obvious Decisions). `move_in_acked_at`/`move_out_acked_at` (`scripts/add-tenant-transition-ack.sql`) hold the landlord's confirmation that a move actually happened, which is what dismisses it from the dashboard
- `properties` - rental properties with address, type, unit count, Google Drive link. `in_production` (default `true`) retires a property from active tracking when unchecked — see Non-Obvious Decisions
- `contracts` - lease agreements between tenants and properties
- `payments` - payment records with Stripe integration
- `maintenance_requests` - tenant-submitted maintenance requests. The landlord views these as the **To Do List** kanban board (Trello-style, 3 columns New/In Progress/Closed via `@dnd-kit`); drag-to-move writes `status`. Stored status values are unchanged (`new`/`in-progress`/`closed` + legacy `resolved`/`open`); the board maps them onto columns. The tenant portal still shows a plain submit-and-track list. Nav label is split: landlord = `navTodo` ("To Do List"), tenant = `navMaintenance` ("Maintenance"). `closed_at` records when a ticket was closed (see Non-Obvious Decisions)
- `email_settings` - landlord email automation config
- `units` (Phase 2) - individual units per property with bed/bath/rent. Writes go through the `lib/units/` seam. The `status` column is **write-only legacy**, same as `tenant_profiles.status` — occupancy is derived from the unit's tenants on read (see Non-Obvious Decisions)
- `documents` (Phase 2) - uploaded files with AI-extracted metadata
- `email_templates` - named, reusable email templates with `{merge_tag}` placeholders
- `email_automations` - date-triggered rules: `event_type`, `offset_days[]`, `template_id`, `scope`, `enabled`
- `email_messages` - outbound send log + inbound replies; tracks delivery/open/reply status. Partial unique index `(automation_id, tenant_id, event_type, event_date, offset_days)` makes the cron idempotent (the index excludes `status='draft'` rows so batch drafts don't claim a send slot). `batch_id` links a row to a review batch
- `email_batches` - one row per "Run now" human-review send (`scripts/add-email-batches.sql`). Parent of draft `email_messages` rows; `status` (draft|sent|cancelled). The resumable review batch + audit record. RLS gated on `is_team_member(landlord_id)`
- `lease_renewals` - one row per renewal attempt (DocuSeal workflow). Serves as the review queue, the renewal chain, and the audit trail. Holds `original_lease_date` (immutable "X date" pinned at the chain root), derived new term, carried rent, `status` (draft|pending_review|sent|signed|countersigned|declined|blocked), `docuseal_submission_id`, and `signers` jsonb. RLS gated on `is_team_member(landlord_id)`
- `parking_spots` - one row per physical spot (`scripts/add-parking.sql`). `market_status` (tenant_priority|open_market, CHECK-constrained) is a real branching vocabulary; `type` is the layout picklist from `SPOT_TYPES` (see Non-Obvious Decisions) and is *not* CHECK-constrained. `car_make`/`car_model`/`car_year` describe the vehicle parked there — attached to the spot, not the lease. Unique `(property_id, label)`
- `parking_renters` - market lessees who are **not** tenants. Deliberately has **no `auth.users` link**, so nothing in the write path can give a market renter portal access
- `parking_leases` - the **parking lease**: the agreement for one spot. A separate record from `contracts` (the residential lease) with **no link between them** — see CONTEXT.md for why that's deliberate. A `CHECK` enforces exactly one of `tenant_id`/`renter_id`, so a parking lease is never ambiguous about who it's for; an `EXCLUDE` constraint prevents two leases double-booking a spot over overlapping dates at the DB level. Occupancy is **derived** from `start_date`/`end_date` via `lib/parking/status.js`, never stored

Note: `email_settings` (payment reminders) is a separate, older feature — the "Payment Reminders" nav item. The new "Email Automation" nav item is the `email_templates`/`email_automations`/`email_messages` system above. Keep them distinct.

## Key Conventions
- Naming: Next.js App Router conventions (page.js, layout.js, route.js)
- Files: pages in `app/`, API routes in `app/api/`, shared code in `lib/`
- Data mappers convert snake_case (Supabase) to camelCase (UI). For **seamed** entities (maintenance, tenant, property, payment-reminders) the mapper is the one home in `lib/<entity>/mappers.js` and `fetchAllData` imports it; the remaining (un-seamed) entities still define their mapper inline in `fetchAllData` in `property-management-app.jsx`
- Reusable UI components: Modal, Inp, Sel, Btn, Badge, Icon, PageHeader, StatCard, Toggle
- **Inline-style dedupe**: styling is 100% inline objects (no CSS classes), so hoisting is the DRY mechanism. When the same inline-style object repeats within a component file, hoist it to a file-level `const` (e.g. `dangerIconBtnStyle`, `PRIORITY_COLORS`, `emptyCard`, `footerRow`) and spread it, overriding only the differing field, rather than duplicating the literal. Keep the const in the file that uses it — do not add a cross-file shared-style module (the circular-import component files stay self-contained). Note `Btn` only spreads `{ children, onClick, variant, size, icon, disabled }` — a `style` prop passed to `<Btn>` is silently dropped, so use `variant` for color.
- Bilingual support: English and Chinese via T object (landlord UI only)
- **Translation rule**: Every user-facing string in landlord UI JSX must be added to both `T.en` and `T.zh` in the T object at the top of `property-management-app.jsx` before use. Reference it as `t.keyName` — never hardcode visible text directly in JSX. When adding a new page or feature, add all its strings to both language blocks as the first step. This applies to **every** visible string the landlord can see: page titles, table headers, button labels, modal titles and bodies, confirmation prompts, empty-state messages, error/toast messages, badge text, placeholders, and tooltips. The only exceptions are dynamic data values from the database, brand names, and currency/date output already shaped by `fmt` / `fmtDate`.
- Run dev server: `npm run dev` (localhost:3000)

## Non-Obvious Decisions
- **Two routing models, by surface.** The public surfaces (marketing + auth, in route groups `(marketing)`/`(auth)`) are real Next.js route files with URL routing. The authed app is the opposite: the entire landlord/tenant UI lives in one JSX file (`property-management-app.jsx`), mounted at `/dashboard`, with **state-driven** navigation (`page` state variable), not per-view URLs. So "add a public page" = new route file; "add a dashboard view" = new case in `renderPage()`.
- **Per-entity data-access seam.** Newer entity writes don't call `supabase.from(...)` inline in the monolith — they go through a `lib/<entity>/` module: a React-free `core.js` (write ops, takes an injected adapter), `adapter.js` (real, over the anon client) + `fake.js` (in-memory, for tests), and `mappers.js` (read-shape). The monolith calls the core via a `use<Entity>Mutations()` hook that owns the optimistic update + rollback. Done for `maintenance`, `tenant`, `property`, `payment-reminders`, `parking`, `units`; the rest (payments, contracts, documents — mostly already routed) still write directly. **New write code for a seamed entity goes through its seam; new direct `supabase.from(...)` writes in the monolith are the thing this replaced.** Hooks use plain consts (the React Compiler memoizes — manual `useMemo`/`useCallback` triggers a "memoization could not be preserved" lint error).
- `lib/supabase/server.js` uses the service role key (not anon key) for admin operations like creating/updating auth users.
- Google Drive links are stored per-property in `properties.drive_link` and embedded as iframes. Phase 2 adds Supabase Storage for direct file uploads.
- Tenant accounts are created by landlords via API (not self-service signup).
- **Tenant status is derived, not stored.** `future tenant` / `current tenant` / `previous tenant` is computed from `move_in_date`/`move_out_date` by `lib/tenant/status.js` (`statusFor` for camelCase, `statusForRow` for raw rows, `isCurrentRow` for occupancy). Rule: move-out already past → previous; move-in still ahead → future; otherwise current — current through the whole of the move-out day, current on the move-in day, and a null move-in means already resident. There is **no manual override**: to make someone previous you set a move-out date. The `tenant_profiles.status` **column is write-only legacy** — still written on create/update so external SQL and the ops scripts don't see nulls, but never read back. Two consequences that are easy to trip over: (1) occupancy can't be filtered in SQL, so the write routes select `move_in_date, move_out_date` and filter through `isCurrentRow` in JS instead of `.eq('status', 'current tenant')` — and a Postgres `GENERATED` column can't replace this, since the value must change at midnight without a write; (2) `isCurrentRow`/`statusForRow` take `today` as their second argument, so pass `t => isCurrentRow(t)` to `.filter()`, never a bare reference, or the array index is read as the date.
- **`properties.in_production` hides a property's tenants, not the property.** Unchecking "In Production" (add/edit property modal) excludes that property's tenants — and their maintenance requests — from `LandlordDashboard`, `TenantsPage`, `PaymentsPage`, and the To Do List board (`MaintenancePage`). The property itself, and its entry on the Properties page, are unaffected; this is where the flag is toggled, so it can't disappear along with what it hides. `nonProductionPropertyIds(properties)` (defined once in `property-management-app.jsx`, near `PropertyFilterBar`) is the single predicate every one of those pages calls — do not re-derive "is this property excluded" inline. `mapProperty` exposes it as `inProduction`, defaulting `true` so a null or missing column never silently excludes anyone; only an explicit `false` counts. A tenant with no `propertyId` is always visible, since the flag is per-property. `LandlordDashboard` applies this by shadowing the `tenants`/`payments`/`maintenance`/`units` destructured from `data` with filtered locals of the same name at the top of the component — the ~250 lines below read those names unchanged, so a new dashboard calculation gets the exclusion for free without needing to re-derive it.
- **Parking spot type is a JS-enforced picklist, not a DB CHECK — unlike `market_status` in the same table.** `SPOT_TYPES` in `lib/parking/status.js` is the one home, read by both the UI dropdown and `createSpot`/`updateSpot`, which reject an off-list value for every caller (seed scripts, future API routes), not just the dropdown. Adding a fourth layout is a one-line change there rather than a migration. The general test for which to use: the app **dispatches** on `market_status` (tenant-priority vs open-market changes behavior) but only **displays** `type` — values you branch on want DB constraints, values you render want flexibility.
- **A parking spot's vehicle is attached to the spot, not the lease.** `car_make`/`car_model`/`car_year` live on `parking_spots`, so when a lease ends the previous renter's car stays listed until someone clears it, and there's no history of which vehicle occupied a spot when. Chosen knowingly for simplicity over putting them on `parking_leases`. If vehicle history ever matters, that's the migration to make.
- **`updateSpot` cannot move a spot between properties.** Doing so would strand the spot's lease history against a lot it no longer belongs to, and could collide with the unique `(property_id, label)` constraint on arrival. The edit modal renders property read-only and a test asserts a passed-in `property_id` is ignored. Editing is allowed on *leased* spots (renaming doesn't invalidate a lease); deleting is not.
- **The parking lot diagram's geometry is derived from `type`, not stored.** `lib/parking/layout.js` places every stall from the spot's `type` alone — the three `SPOT_TYPES` are the three zones of the lot (right column drawn diagonally, a short back row centered at the top, left column), ordered numerically by label within each zone. There is no geometry column and no label→coordinate map, so a spot appears in the right place purely by being typed correctly, and there's no second source of truth to keep in sync when a spot is added or renamed. The cost: only lots shaped like those three zones are representable. A lot with an island, a second bank of stalls, or a non-rectangular footprint can't be drawn by widening the picklist — it needs real per-spot coordinates on `parking_spots` and a layout that reads them. Until then, an untyped spot is deliberately returned as `unplaced` rather than guessed at, so a missing type shows up as a gap to fix instead of a wrong stall.
- **A unit's `status` column is derived on read, so nothing writes it.** `fetchAllData` recomputes every unit's status from its tenants' occupancy (`isCurrentRow`) and overwrites whatever the column holds, exactly like `tenant_profiles.status`. The add/edit unit modal therefore has no Status field — it used to, and it silently did nothing. `createUnit`/`updateUnit` omit the column; the DB default (`'vacant'`) keeps it non-null for external SQL. Do not add a UI control that sets it.
- **A closed To Do List ticket records when it was closed, and re-closing doesn't rewrite it.** `nextClosedAt` in `lib/maintenance/status.js` owns the rule (stamp on the transition into closed, preserve an existing timestamp, clear on reopen) because two call sites write status — the board drag and the detail-modal dropdown — and both must agree. `setStatus` writes `status` and `closed_at` in one update so a request is never observed closed-without-a-date. Callers pass the row's existing `closedAt`; that argument is what makes re-closing idempotent. `mapMaintenance` exposes both `closedDate` (date-only, for `fmtDate`'s local-midnight rule) and `closedAt` (full timestamp, for the write path). Null on tickets closed before the column existed — deliberately not backfilled.
- **Dashboard move-ins/move-outs are dismissed by a human, not by the calendar.** Because tenant status is derived from dates, a Unit Transitions row used to remove itself the moment its date arrived — an incoming tenant flipped future→current and dropped off whether or not they actually showed up. `move_in_acked_at`/`move_out_acked_at` on `tenant_profiles` hold the landlord's confirmation; `awaitingMoveInAck`/`awaitingMoveOutAck` in `lib/tenant/status.js` keep the transition listed until it's set, and the row's "Tenant(s) have moved in/out" button writes it via `acknowledgeMoveIn`/`acknowledgeMoveOut`. Three things that are easy to trip over: (1) acknowledging is **one-way** — there's no un-acknowledge, because the fix for a move-in that didn't happen is to change the date, the source of truth every other rule reads; (2) `awaitingMoveInAck` returns false for a tenant who has already moved out, so importing a historical tenancy doesn't put a departed tenant in the "moving in" column; (3) like the other predicates here, `today` is the second argument — pass `x => awaitingMoveInAck(x)` to `.filter()`, never a bare reference.
- **Landlord teams**: `user.id` in the client app is the **team's `landlord_id`**, not the auth user's id. `user.authId` holds the actual `auth.uid()`. Login resolves the team via `landlord_members`. Inserts that set `landlord_id` should always use `user.id`, never `user.authId`. RLS uses `is_team_member(landlord_id)`.

## Common Tasks
- **Run locally**: `npm install && npm run dev`
- **Add a dashboard view**: Add a case to `renderPage()` in `property-management-app.jsx` and a nav entry in `Sidebar`
- **Add a public (marketing/auth) page**: Create a route file under `app/(marketing)/` or `app/(auth)/`; reuse tokens from `lib/theme.js` and the `Logo` from `app/_brand.jsx` (keep marketing pages as server components so they don't pull in the client monolith)
- **Add an API route**: Create `app/api/<route>/route.js`
- **Add a data entity**: Add Supabase table, mapper function, fetch in `fetchAllData()`, and entry in `data` state
- **Add/change a write for a seamed entity** (maintenance, tenant, property, payment-reminders, parking, units): add the op to that entity's `lib/<entity>/core.js` (+ a test against `fake.js`), expose it on the `use<Entity>Mutations()` hook, and call the hook from the component — don't add a direct `supabase.from(...)` write
- **Seam a new entity**: mirror `lib/maintenance/` — `core.js` + `adapter.js` + `fake.js` + `mappers.js` + `*.test.mjs`, a `use<Entity>Mutations()` hook in the monolith, point `fetchAllData` at the mapper, and add the test glob to `package.json`

## Do Not
- Do not create separate Next.js page files for **authed app views** - use the state-driven navigation pattern in the monolith (mounted at `/dashboard`). This does NOT apply to the public marketing/auth surfaces, which are intentionally real route files.
- Do not use the anon key in server-side API routes that need admin access (use service role key via `lib/supabase/server.js`)
- Do not add new direct `supabase.from(...)` writes (or duplicate a snake→camel mapper) in the monolith for a **seamed** entity — route them through the entity's `lib/<entity>` seam + `use<Entity>Mutations()` hook
- Do not duplicate the `fmt`/`fmtDate`/`daysBetween` formatters — import them from `lib/format` (the canonical home)
